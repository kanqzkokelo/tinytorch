# Road to 270 tok/s Implementation Plan

> Execution note: implement this task-by-task.

**Goal:** Take tinytorch's Qwen2.5-0.5B decode from 75.6 tok/s to **≥270 tok/s decode-only** (short context), with the m61 logit-parity gate green after every single change.

**Architecture:** This is a bandwidth campaign, not a feature build. The step budget at 270 tok/s is 3.7 ms, which requires sustaining ~108 GB/s across the full 400 MB of per-token weight reads. Today's average is ~30 GB/s. The lm-head fix proved 110 GB/s on this chip is reachable; the campaign generalizes that fix to the 253 MB of q4_0 layer GEMVs, then attacks residual latency gaps. Work is strictly profile-driven: no kernel is touched until Task 1's profiler shows it is worth touching, and every variant passes `verify.sh m61` before it is kept.

**Tech Stack:** CUDA 12 (sm_86), `kernels/gemv_q4_cuda.cu` + `kernels/qwen2_cuda.cu`, CUDA events for in-graph timing, nsight-compute if available (`$HOME/mmcuda` may ship `ncu` — detect, don't assume), existing `bench_llm.py` + `tests/gate_m6_logit_parity.py`.

**Working branch:** `m6-correctness` (same checkout; oracle + fixtures live here).

**Honest framing (read before starting):**
- 270 tok/s = 70%+ of the 108 GB/s-average requirement met at *every* stage. Expect the ladder to go ~75 → 120 → 180 → 240 → 270 through independent wins; some stages may plateau below target. The gate for THIS plan is the measured number, recorded honestly — if we land at 220 and two consecutive tasks add <3%, write BLOCKED.md per house rules rather than fake it.
- Context dependence: numbers quoted are for ≤64-token contexts. Attention grows linearly with context; document the decay curve in Task 7 rather than pretending it doesn't exist.

## Task 0: Per-kernel profiling harness

You cannot optimize 15 kernel types blind. Build an in-graph event-timing table.

**Files:**
- Create: `tools/profile_step.cu`
- Modify: `bench/results.md`

**Step 1: Kernel timing tool**

Create `tools/profile_step.cu`: loads the engine exactly like `tools/dump_logits.c` (copy its init block: gguf_load → tt_config_from_gguf(m,1024) → create → prefill tokens from argv), then:

```cuda
/* wrap ONE replayed step with events, repeated K times */
cudaEvent_t e0, e1;
cudaEventCreate(&e0); cudaEventCreate(&e1);
/* warmup 3 replays via the same sequence dump_logits uses (next() twice, discard) */
float best = 1e9f;
for (int k = 0; k < 20; k++) {
    cudaEventRecord(e0, e->stream);
    /* one next()-equivalent: H2D pending tok, graph launch, D2H, sync */
    ... same calls as qwen2_engine_next replay path ...
    cudaEventRecord(e1, e->stream);
    cudaEventSynchronize(e1);
    float ms; cudaEventElapsedTime(&ms, e0, e1);
    if (ms < best) best = ms;
}
printf("STEP_MS %.3f\n", best);
```

If `e->stream` internals aren't exposed, add a minimal public hook in `include/qwen2_engine.h`: `int qwen2_debug_replay_step(Qwen2Engine*, int next_tok);` that performs one graph-replayed step and returns the sampled id — implemented in `kernels/qwen2_cuda.cu` by refactoring the replay body out of `qwen2_engine_next` so both share it (no duplication).

**Step 2: Per-stage breakdown**

For attribution without ncu, temporarily bracket stages with events INSIDE forward_layers guarded by `getenv("TT_PROFILE")`: record elapsed ms for {embed, per-layer-group Q/K/V GEMVs, O+MLP GEMVs, flash, rmsnorm-family, scatter, logits-GEMV, argmax}. Print a median-of-20 table. This instrumentation is temporary — gate it behind the env var and keep it (cheap, useful forever).

Run: `TT_PROFILE=1 ./build/profile_step 785,6722,315,9625,374`
Expected output: a table whose rows sum to ≈13.2 ms. Record it verbatim in `bench/results.md` under `## M6.3b profile baseline`. This table decides Task priorities below — if flash-attn is >10% at pos≤5, something is wrong with it; if logits-GEMV >1.4 ms, Task 2 matters more than planned.

## Task 1: q4_0 layer-GEMV bandwidth campaign (the main prize)

Layer weights are 253 MB/token — bigger than the LM head. Whatever made `k_logits_q8_0` 4× faster applies here with q4_0-specific twists.

**Files:**
- Modify: `kernels/gemv_q4_cuda.cu` (`k_gemv_q4_0`, launcher grid math)
- Test: `./scripts/verify.sh m61` + `python3 bench/bench_llm.py --runs 3 --tokens 64`

**Step 1: Reproduce the lm-head winning pattern on q4_0**

Current inner loop does 16 scalar `qs[i]` byte loads per 18-byte block. Apply the two proven fixes:
- **x loads via float4**: each lane owns 32 consecutive floats of x per block-stride iteration… careful: lanes stride by BLOCKS (b += 32), each lane reads x[b*32 .. b*32+31]. Convert to `float4` loads: `reinterpret_cast<const float4*>(xb)[i]` giving 8 float4 loads instead of 32 scalars.
- **W nibble loads via uint32**: `blk.qs` viewed as `uint32_t[4]`; unpack low/high nibbles per byte with shifts, convert with `__int2float_rn`. Alignment: row stride = nb*18 bytes; nb=28 → 504 B (≡8 mod 16), nb=152 → 2736 B (≡0 mod 16), nb=12 (K/V proj, K=384? verify per-matrix) — handle the mod-8 case with `__byte_perm` merge exactly like the lm-head implementation did (that code already solved this; copy its approach and comment style).

**Step 2: Variant ladder with revert discipline**

Try in order, one commit each, keeping only ≥2% wins (same rules as the lm-head task):
- V1: float4-x + uint32-W (port of lm-head winner)
- V2: two rows per warp (halves x re-read pressure, doubles rows in flight)
- V3: `#pragma unroll` sweep on the b-loop (2/4/8)
- V4: blockDim.y 16 vs 8 vs 32 (lm-head taught us 32 HURTS on this GPU — include 8 too)
- V5: only if profile shows q-K/V GEMV specifically slow: fold k_bias/v_bias adds into the GEMV epilogue (removes 2 launches × 24 layers)

After EVERY variant: rebuild, `./scripts/verify.sh m61` (must stay 7/7), `python3 bench/bench_llm.py --runs 3 --tokens 64`. Revert anything <+2%. Track each attempt in results.md even the failures (that table caught real patterns last time).

**Step 3: Expected outcome**

Layers drop from ~253 MB at ~40-60 GB/s toward 110-140 GB/s ⇒ layer time from ~5 ms to ~2 ms. Overall step should land ~8–9 ms (≈115–125 tok/s) after this task alone.

**Step 4: Commit per kept variant**

```bash
git commit -am "M6.3b: q4_0 GEMV V<n> — <delta> tok/s (parity intact)"
```

## Standing rules (inherited, non-negotiable)

- `./scripts/verify.sh m61` green after EVERY kept change; revert anything that breaks it.
- Never stack unverified optimizations.
- Eager fallback path (`TT_NO_GRAPH=1`) stays functional.
- All numbers via `bench_llm.py` (which enforces parity internally); hand timings don't count.

## Explicit non-goals

- Quantizing x activations (numerics sign-off required — separate decision)
- Batching, speculative decoding, multi-GPU
- Touching tokenizer/loader (done, verified)
