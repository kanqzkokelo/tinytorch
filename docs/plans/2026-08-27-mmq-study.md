# MMQ/MMVQ study: why llama.cpp CUDA decode scales better (0.80× @135m → 0.25–0.32× @1b)

Date: 2026-08-27 · READ-ONLY study of `oracle/llama.cpp/ggml/src/ggml-cuda/*` vs
`kernels/gemv_q4_cuda.cu`, `kernels/gemv_typed.cu`, `kernels/qwen2_cuda.cu`.
Measured context: REALITY CHECK in `2026-08-26-m9-m11-roadmap.md`,
`data/bench/results_scoreboard_cuda.jsonl`. GPU: RTX 3050 Laptop, cc 8.6 (Ampere, 16 SMs,
peak DRAM ≈ 192 GB/s theoretical).

## 0. Measured frame (derived from scoreboard)

weights_bytes / median_tok_s = effective per-token weight-streaming rate:

| model | size | ours | oracle | ours GB/s | oracle GB/s |
|---|---|---|---|---|---|
| smollm2-135m q4_0 | 91.7 MB | 346.7 t/s | 442.8 | 31 | 41 |
| smollm2-135m q8_0 | 144.8 MB | 143.0 | 466.1 | 20 | 67 |
| qwen2.5-0.5b q4_0 | 428.7 MB | 222.8 | 279.3 | **95** | 111 |
| qwen3-0.6b q8_0 | 639.4 MB | 48.7 | 194.3 | 49 | 124 |
| llama-3.2-1b q4_0 | 773.0 MB | 58.6 | 183.0 | **45** | **142** |

Reading: at 135 m neither side saturates (per-token latency floor dominates → ratio ≈ 0.8).
As tensors grow, oracle climbs monotonically toward the DRAM wall (~142 GB/s ≈ 74 % of
peak); WE PEAK AT ~95 GB/s AT 0.5b AND REGRESS TO 45 AT 1b. The gap is not "they are
faster everywhere"; it is that their decode time tracks weight bytes while ours stops
scaling. Everything below explains that divergence from source.

## 1. Anatomy of their decode path (ne11 == 1, one token)

Dispatch (`ggml-cuda.cu::ggml_cuda_mul_mat`): quantized src0 + F32 src1 +
`ne11 <= MMVQ_MAX_BATCH_SIZE (=8)` ⇒ **MMVQ**, NOT the tile-MMQ kernel. For decode the
famous MMQ shared-memory tile kernels never run; `ggml_cuda_should_use_mmq` is bypassed
by the earlier `ggml_cuda_should_use_mmvq` branch. Tile-MMQ (`mmq.cu`) only takes over at
batch ≥ 9 (prefill territory). File: `mmvq.cu`.

Per mul_mat call, two launches:

1. `quantize_row_q8_1_cuda` — quantizes the x-vector fp32 → `block_q8_1`
   (int8 quants + half2 {d, partial-sum-of-x}) once into a pool buffer. Cost ∝ K only.
   NOTE: they pay this per tensor (7+ calls/layer) and still win.
2. `mul_mat_vec_q<type, ncols_dst=1>` — dequant-in-register GEMV against q8_1 y.

### Kernel config for q4_0 [1536,1536] × [1536]

- Parameter table `MMVQ_PARAMETERS_GB10` (cc ≥ Ampere, `get_device_table_id`).
- `ncols_dst==1`: base `nwarps = 4`; `should_halve_iters()` heuristic
  (blocks_per_row_x = 1536/32 = 48; iters=2 → wide iters_wide=1, idle=0 ≤ budget)
  promotes to **nwarps = 8** ⇒ block = (32 lanes × 8 warps) = 256 threads.
- `rows_per_cuda_block = 1` ⇒ grid.x = M = 1536 blocks, one output row per block,
  8 warps cooperating over the K loop (`kbx += blocks_per_iter`,
  blocks_per_iter = vdr·nwarps·32/qi = 2·8·32/8 = 64 > 48 ⇒ each thread touches
  exactly one 32-value block).
- Inner product `vec_dot_q4_0_q8_1` (`vecdotq.cuh`): VDR_Q4_0_Q8_1_MMVQ = 2, i.e. each
  thread loads **2 × uint32 = 8 weight-byte payload**, masks nibbles
  (`(v>>0)&0x0F0F0F0F`, `(v>>4)&0x0F0F0F0F`) and does **4 × __dp4a int8-SIMD MACs**
  against the pre-quantized q8_1 y words; integer accumulator; one fp32 rescale per
  chunk using half2 ds (the −8 bias folds into `ds.y * 8·vdr/QI4_0`). Zero fp32 FMA in
  the hot loop, zero int→float converts.
- Weight bytes/thread/loop-cycle: 8 B qs (+8 B y ints + shared d/ds).
  Whole-row bytes/thread: 864 B / 256 ≈ 3.4 B.
- lm_head [262144,1536]: **same kernel, grid.x = 262144 blocks**. No split-K anywhere —
  M is so large that plain row-parallelism saturates DRAM; split-K would only add
  reduction traffic. (Hypothesis (b) below: disproven.)
- GLU fusion (`ggml_cuda_should_fuse_mul_mat_vec_q` + fusion args): gate+up matrices in
  ONE launch, second accumulator `tmp_gate`, SiLU/GeGLU epilogue in-register, optional
  bias fusion. FFN pays one launch and streams x once.
- PDL (`ggml_cuda_pdl_sync/lc`): compiled but no-ops below Hopper — irrelevant on cc 8.6.

### Same-shape config for q8_0 / K-quants

Identical template machinery; per-dtype specialization lives entirely in
`vec_dot_q*_q8_1` (each with tuned `VDR_*_MMVQ`: q8_0 VDR=2, q4_K VDR=4 …) and the
per-arch nwarps tables (Turing/GB10/RDNA…). One code path, per-dtype inner dots.

### Ours, same shapes

- Layers q4_0: `k_gemv_q4_0` V2 (`gemv_q4_cuda.cu`): block (32,16)=512 thr, 2 rows/warp,
  grid M/32; uint32 weight words + `__byte_perm` alignment fixups; **fp32 FMA chain**
  (16 FMAs per word per row, serial dependency on s0/s1); x re-read as float4 per warp.
- FFN: fused gate/up exists (`tt_ffn_q4_0`) — parity with their fusion, q4_0 only.
- **Logits: `k_logits_q4_0` is the OLD scalar kernel** (per-byte `blk.qs[i]` loads,
  BlockQ4_0 struct copies, no vectorization). The V2 treatment was applied to layer
  GEMVs and `k_logits_q8_0` only. `tt_logits_dispatch` routes q4_0 there.
- q8_0 layers: `tt_gemv_typed` → `k_gemv_q8_0` = **scalar byte loop** (34-byte blocks,
  32 separate int8 loads + 32 fp32 FMAs per block) — never got the V2/dp4a work.
- K-quants (q4_K/q6_K…): straightforward scalar ports in `gemv_typed.cu`.
- Engine: cudaGraph capture EXISTS (`qwen2_cuda.cu` M6.3) ⇒ raw launch overhead is
  already amortized; but inside the graph, `k_rmsnorm<<<1,256>>>` runs ONE BLOCK for the
  whole GPU (grid=1!) twice per layer, and rope/scatter/add micro-kernels serialize.

## 2. Why their advantage SCALES with model size

Mechanism: at 135 m both sides sit on the per-token latency floor (kernel-count ×
launch/DRAM-latency), ratios land 0.25–0.8 regardless of kernel quality. As width/depth
grow, runtime shifts to the streaming regime where achieved GB/s = min(DRAM, instruction
throughput per byte × occupancy). Their design keeps instruction work per weight byte at
~1 dp4a + 2 shifts per 8 values and reaches ~142 GB/s; ours plateaus ~95 and regresses
because slow-path share grows with vocab×dim and depth.

Ranked root causes (code-verifiable):

1. **Inner-loop instruction economics (dominant).** Ours: per weight value =
   nibble extract + shift + int→float convert + fp32 FMA, chained on 2 accumulators
   (ILP-limited). Theirs: prequantized q8_1 y + __dp4a ⇒ 4 int-MACs/instruction, fp32
   only at chunk boundaries. In the latency-floor regime this is hidden; in the
   streaming regime it caps our ceiling ~30 % under theirs and gets WORSE per byte as
   more of the step is GEMV streaming.
2. **Untuned dtype paths whose cost share grows with size.**
   - q8_0: ALL layer matmuls go through scalar `k_gemv_q8_0` ⇒ 20–49 GB/s effective
     end-to-end (scoreboard), ratio 0.25–0.31 at EVERY size — and absolute gap widens
     as layers deepen.
   - Logits: `k_logits_q4_0` scalar kernel streams the largest tensor in the model
     (135m: 16 MB → 1b: 148 MB; 0.5b: 76 MB). Its share of step time grows with
     vocab×dim exactly where the ratio collapses (0.80 → 0.32).
   - K-quants: scalar ports, same story for q4_K/q6_K families.
3. **GLU/bias fusion breadth.** Their fusion covers any quant type incl. biases;
   ours only q4_0 gate/up. At 1b the FFN up+gate pair is ~2/3 of layer bytes, and their
   single-pass x reuse halves L2 pressure there.
4. **Launch/micro-kernel serialization (minor post-graphs).** Graph capture killed raw
   launch overhead, but `k_rmsnorm<<<1,256>>>` (one block for 16 SMs) and the
   rope/scatter/add train still serialize inside the captured region; their equivalents
   are multi-block/fused. Cost grows with dim (2048-wide norms at 1b vs 576 at 135m).
5. **Disproven / irrelevant hypotheses:**
   - (b) lm-head split-K: none exists in their MMVQ; huge-M parallelism suffices.
   - (c) L2 persistence: zero `accessPolicyWindow`/persisting-L2 usage anywhere in
     ggml-cuda.
   - (e) precision/ILP from fp32-vs-int accumulate: backwards — THEIR hot loop is int32
     with shorter dependency chains; our fp32 FMA chain is the ILP-handicapped one. This
     is cause #1 restated, not an independent effect.
   - (a) "K-quant kernels relatively better": true but subsumed by #2 — the scoreboard
     shows the q8_0 gap already maximal at 135 m (fixed deficit), while the q4_0 gap
     GROWS with size (scaling deficit). Two different diseases; #1+#2 cover both.

## 3. Port plan — the ONE kernel change with biggest expected win

**Port the MMVQ dequant-in-register GEMV with prequantized-q8_1 activations and
__dp4a dot products, and route BOTH layer GEMVs AND logits through it.**
This is one kernel family (template on dtype like `vec_dot_q*_q8_1`) replacing four
call sites (`k_gemv_q4_0` layers, `k_logits_q4_0`, `k_gemv_q8_0`, later typed K-quants).
It attacks causes #1 and #2 simultaneously and matches their measured endpoint
(~142 GB/s effective at 1b-class shapes).

Sketch (q4_0 variant):

```cuda
// step A (once per token, K floats): x -> block_q8_1 {int8 qs[32]; half2 ds;}
__global__ void k_quant_x_q8_1(const float* x, block_q8_1* y, int K);

// step B: one row per block, NW warps cooperate over K-loop (NW=8 for K>=1024)
template<int NW> __global__ void k_gemv_dp4a_q4_0(const block_q4_0* W,
        const block_q8_1* y, float* out, int M, int K) {
    const int row  = blockIdx.x;                 // grid.x = M
    const int tid  = threadIdx.y * 32 + threadIdx.x;      // 256 threads
    const int nb   = K / 32;                     // 48 for K=1536
    const int bpi  = 2 * NW * 32 / 8;            // blocks_per_iter = 64
    float sum = 0.f;
    for (int kb = tid / 4; kb < nb; kb += bpi) { // qi/vdr = 8/2 = 4 threads/block
        const int   iqs = 2 * (tid % 4);         // 2 ints per thread
        int  v[2], sumi = 0;
        load2_int32(v, &W[row*nb + kb], iqs);    // 8 weight bytes, coalesced
        #pragma unroll
        for (int i = 0; i < 2; ++i) {
            sumi = __dp4a(v[i] & 0x0F0F0F0F, y[kb].qs[4*i+0], sumi);
            sumi = __dp4a(v[i] >> 4 & 0x0F0F0F0F, y[kb].qs[4*i+1], sumi);
        }
        const float2 ds = __half22float2(y[kb].ds);
        sum += W[row*nb + kb].d * (sumi * ds.x - 8.f * ds.y);
    }
    // warp reduce + cross-warp reduce via smem[NW-1][32] (as in mmvq.cu)
}
// q8_0 variant: v = 2 raw int8 words, dp4a straight against y ints, VDR=2.
```

Integration: `tt_logits_dispatch` + `tt_gemv_typed` delegate here; keep old kernels
behind `TT_OLD_GEMV=1` for A/B; parity gate = existing logit-parity checks
(`scripts/verify.sh`), bench gate = scoreboard rerun.

**Predicted result:** their end-to-end numbers on identical hardware/shapes are the
upper bound: q4_0 layers+head ~140 GB/s effective ⇒ llama-3.2-1b decode ≈ 175–185 t/s
parity (ratio 0.32 → ~0.95–1.0); qwen3-0.6b q8_0 ≈ 170–190 t/s (ratio 0.25 → ~0.9).
Even a conservative 60 % transfer of their advantage puts us ≥ 0.75× everywhere.
Secondary follow-ups (separate tasks, do NOT bundle): multi-block rmsnorm, GLU fusion
for the dp4a path (we already have the epilogue pattern in `k_fused_swiglu_q4_0`),
K-quant vec_dots (q4_K first).
